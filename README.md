# route_profile_feed — 営業圏プロファイル（電話帳）の置き場

タクログの**電話帳**を配る置き場。アプリはここを見て「その営業圏で、どこに何を
聞きに行くか」を決める。

| 中身 | 何に使うか |
|---|---|
| `weatherAreaCode` | 気象庁に聞く時の地点番号（天気） |
| `yahooAreaCode` / `individualLines` | Yahoo!に聞く時のエリア番号と路線ページ（運行情報） |
| `home` / `adjacent` | 出庫前に地図を寄せる中心と半径・イベント会場の関連度判定 |
| `trainLineNames` / `trunkLineNames` / `fullOperators` | その営業圏に関係する路線の名簿 |
| `boundaryDirs` | この電話帳が担当する営業圏キー（運賃メーターで選ぶもの） |

## 🔴 これが無いと何が起きるか

**その営業圏では、電車タブと天気チップが画面にそもそも出ない。**
時刻表を配っても見えない（アプリが「この街のことは何も知らない」と判断するため）。
2026-08-15 時点で 83営業圏のうち**38圏しか電話帳が無い**＝これが全国展開の
いちばんの足かせだった。

## 営業圏を1つ足す手順

1. `src/<営業圏キー>.json` を1枚作る（既存ファイルを写して直すのが早い）
2. `python3 build.py` を回す。**検査に1つでも引っかかれば止まる**
3. 緑になったら commit → push。Actions が検査し直して Pages へ配る
4. アプリ側は**何も変えなくてよい**（次の起動で降ってくる）

⚠️ アプリ同梱のシード（`route_timer_app/assets/area_profiles.json`）は
ハブに届かない時の最後の砦。区切りの良いところで
`flutter test test/tools/dump_area_profiles.dart` を回して揃えておく。

## 検査していること（build.py）

- 必須項目があるか／`key`・営業圏キーが重複していないか
- **アプリが知らない営業圏キーを書いていないか**（誰にも届かない静かな失敗を防ぐ）
- 天気の地点番号が6桁か
- Yahooのエリア番号が 2〜9 か
  （2=北海道 3=東北 4=関東 5=中部 6=近畿 7=九州 8=中国 9=四国。
  ⚠️ **北陸信越は中部・沖縄は九州**）
- 座標が日本の範囲か・半径が正の数か
- 運行情報の行が `[URL, 表示名, 事業者キー]` の3つ組で、URLの形が正しいか

## アプリ側の受け取り方

`lib/services/area_profile_registry.dart`。4段構えで必ず答えが出る：

1. 端末キャッシュが24時間以内 → それ
2. ネットで取れた → それ（キャッシュ更新）
3. ネット失敗 → 古い端末キャッシュ（圏外でも動く）
4. どれも無い → **アプリ同梱のシード**

🔴 **営業圏の数が減る差し替えは受け取らない。** 一度の事故で街が消えると、
次からは「本当に無い」ので永久に戻らなくなる（2026-08-15、時刻表の長崎が
11日間消えて実際に起きた）。増える方向は正常なので通す。

🔴 **項目の追加は自由**（古いアプリは知らない項目を無視する）。
意味を変える・項目を消す時は `version` を上げるのではなく
**ファイル名ごと変える**（`profiles_v2.json`）。
